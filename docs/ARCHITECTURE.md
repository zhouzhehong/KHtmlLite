# KHtmlLite 架构章程（Architecture Constitution）

> 定位：以 Apple Safari/WebKit 的**机制与设计哲学**为对标对象的 KHTML 双进程浏览器。
> **红线：不抄一行 WebKit/Safari 源码**（许可证与心智负担都不允许）。我们学习的是
> 公开文档、WWDC 讲座、KDE/历史 KHTML 代码与通用的调度/隔离思想，然后重写自己的实现。
> 本文件是规则，不是愿望——任何新代码都必须说明自己对齐了哪一条，或在评审时修改之。

## 0. 北星指标（先立数，后立码）
- 稳定性：任何网页崩溃 **不得**带垮浏览器 EXE 与其余标签页。
- 速度：冷启动到首帧 ≤ 2s；空闲 CPU 占用 ≈ 0；滚动期间帧率稳定 60fps。
- 纪律：所有性能假设必须经过真实机器测量（STARTUP_MARK / 协议计数）才算数，
  禁止"感觉好像更快"。

## 1. 进程与沙箱模型（对齐 WebKit 的多进程职责划分）
- `khtml_browser.exe` = UI/合成器进程。永远不得直接渲染页面内容。
- `khtml_renderer.exe` = 每标签一个渲染进程。崩了只崩一格，自带重载 UI。
- 两条边界：**QLocalSocket（命令/事件，JSON 行协议）+ QSharedMemory（像素数据，
  零拷贝单向传输）**。不允许渲染进程往 UI 里 poke 裸窗口句柄。

## 2. 渲染调度（对齐 Safari 的显示驱动绘制思路）
- 渲染进程有且仅有一个 **显示帧钟**（当前 16ms）：所有 layout/paint 只在这个钟上发生。
- 像素只在**脏矩形**上重画；tile 网格（256×256）以内容哈希抑制重复上传。
- 滚动 = **预测合成**（浏览器先挪画布）+ **权威收敛**（渲染进程稍后以绝对滚动偏移校准），
  保住 60fps 手感，数学上可证明最终一致。

## 3. 墓碑机制（对齐 iOS Safari 的标签页冻结/缩略图恢复机制）
我们的命名分解（不照贴 Apple 原文，借其意）：
- **活页**：完整进程 + 实时渲染。
- **冷藏页**：进程被冻结/或已退出，**保留** 最后一张缩略图 + 完整滚动状态（scrollX/Y、
  zoom、URL、标题），重进时按所见即所得瞬时恢复。
- **处决策略**：内存预算触发。逐页降级，而不是全局崩溃；**最近最少使用**先被墓碑。
- 任何墓碑恢复不得改变用户视觉状态（位置/缩放/Tab 标题）或丢未提交输入。

## 4. CPU 调度与空闲律
- 所有周期性工作**必须可证明需要什么节奏**：帧钟 16ms、内存巡视 10s、网络 keep-alive
  由系统决定。没有"反正 100ms 就转一圈"的轮询。
- 每标签渲染进程挂起时 CPU 占用 = 0（QProcess::suspended/暂停计时器；不是"装作停摆"）。
- 大量一次性工作（首启解析、字体枚举、Bublé 转译）必须被显式授权、可被取消、
  可被测量——不允许在 UI 主线程"顺便"做完。

## 5. 渐进暴露与防御（对齐 Safari 的 RSS 安全防护思想）
- 渲染进程无法执行特权动作（文件写、外部 URL 打开必须经 UI 进程审批）。
- 任何从网络来的字符串/JSON 在渲染进程内先 schema 校验再进 DOM/JS 引擎。
- 崩溃自愈排序：**禁 JS 重载一次 → 展示墓碑/崩溃页 → 用户触发重开**。

## 6. 我们**不**做什么
- 不引入 JIT、不去"重写渲染器"、不把 KHTML 魔改成现代 Web 引擎。它的立身之本是
  轻、稳、可审计；复杂现代站点宁可降级渲染也不硬上。
- 不抄 WebKit 源码、类名、文件布局——我们从行为与机制层对齐。

## 7. 验收判据（每一轮开发必须回答）
1. 这波改动让**哪个**指标变了？放数字。
2. 崩了会怎样？（写进崩溃路径测试）
3. 挂起/墓碑后视觉状态完全保留吗？（写进墓碑协议测试）
